
# YouTube 播放故障与 FreeTube 实现对照（当前状态：2026-10-23）

本节更新较早的工程记录。FreeTube 对照源码快照为 `<本机对照目录>`，Git 提交 `c891861`；Seamind 的 PO token 和 SABR 代码是在那份早期记录之后加入的。播放仍以真实端到端结果为准。

## 代码路径差异

| 环节 | FreeTube（本地快照） | Seamind（当前工作树） | 实际差异 |
|---|---|---|---|
| YouTube 接口 | `src/renderer/helpers/api/local.js:createInnertube`，使用 `youtubei.js` | `apps/desktop/src/youtube-native.ts`，使用 `youtubei.js` 并按客户端尝试解析 | 基础 InnerTube 库相同，客户端选择和与播放器的衔接不同 |
| PO token | `src/main/poTokenGenerator.js` 的 `sharedInit`、`generatePoToken`、`internalGeneratePotoken`；Electron 隔离 session 中运行 Chromium，队列化生成并清理 session | `youtube-botguard.ts` 获取页面 attestation、请求 WAA challenge；`src-tauri/src/youtube_botguard.rs` 创建隐身 Tauri WebView；`youtube-botguard-runtime.ts` 调用 `BotGuardClient` 和 `WebPoMinter` | 两边都使用 `bgutils-js` 4.x。FreeTube 用 Electron `executeJavaScript` 加载本地打包脚本；Seamind 单独下载解释器，再在 YouTube 来源的 WebView 中执行，因而受代理白名单和 Trusted Types 约束 |
| 播放器上下文 | `src/main/poTokenGenerator.js` 给解释器设置代理，并为 InnerTube 和 Google 脚本分别设置 Referer、Origin、Fetch Metadata | Tauri Rust 回环代理集中设置 YouTube Referer/Origin；目标主机需逐项加入白名单 | Seamind 的网络边界更严格；遗漏解释器主机时会在本地被代理以 403 拦下 |
| SABR/DASH | `src/renderer/helpers/player/SabrSchemePlugin.js` 自己构造 ABR protobuf，维护 SABR context、playback cookie、backoff、重试与播放器 reload | `youtube-native.ts` 和 `youtube-sabr-shaka-adapter.ts` 使用 `googlevideo` SABR/UMP 适配器，再由 Shaka 消费 | Seamind 复用协议库，FreeTube 自己掌握更多协议状态；Seamind 这条路径仍需真实 SABR 视频验证 |
| 依赖版本 | `bgutils-js ^4.0.3`、`googlevideo ^4.1.1`、`shaka-player ^5.1.12`、`youtubei.js ^18.1.0` | `bgutils-js 4.0.3`、`googlevideo 4.1.1`、`shaka-player 5.3.1`、`youtubei.js 18.2.0` | 不是依赖缺失造成的主要差异；关键在运行时、代理和协议状态整合 |

## 当前视频的可复现诊断

测试视频 `OBotS2j8fsQ` 的嵌入网络、后端 YouTube 和视频服务器连通性均成功；同一会话中的参考视频也能由 VISIONOS/DASH 解析。目标视频的 VISIONOS、iOS、Android VR 和 Android 请求都收到 `LOGIN_REQUIRED: Sign in to confirm you’re not a bot`，说明是逐视频验证，尚未进入媒体取流。

WEB 客户端尝试 PO token 时，诊断先暴露了两个 Seamind 自身的缺陷，已逐项修复并重启：

1. BotGuard 解释器来自精确主机 `www.google.com`，旧 Rust/前端白名单只允许 `jnn-pa.googleapis.com` 等主机，所以代理本地返回 403。现在仅将 `www.google.com` 加入精确主机列表。
2. 修复白名单后，YouTube WebView 的 Trusted Types 拒绝普通 Blob URL 赋给 `script.src`。现在使用 `seamindBotGuard` 策略，并只允许当前 YouTube 来源创建的 Blob URL。

TypeScript 编译和 Rust 桌面构建均已通过，新版 Seamind 已重新启动。最后一次真实播放确认仍待用户复测；因此目前只能确认应用侧的两个拦截点已修复，不能把播放结果记为已通过。

## 早期方案记录的更正

- 后文“PO token 和 SABR 没做”记录的是 PO token/SABR 代码加入之前的决定，不代表当前工作树。
- QuickJS 仍用于 Google 播放器签名解算；BotGuard 解释器则在隐藏的 YouTube WebView 中运行，两者是不同路径。
- 现阶段若目标视频仍被 YouTube 返回 bot check，应继续看新版 WEB 失败详情和换出口后的同一视频结果；不要将连通性 HTTP 204 当成播放成功。

一、工程问题

外部约束（只能适配，没法消除）
- 机器人验证按视频判定，发生在解析阶段，还没到取流。你当前出口上，我试的 4 个视频只有 1 个能解析。
- 每个请求的固定开销大：你用 TUN 加 fake-ip，TLS 握手约 1 秒，吞吐 0.2–6 Mbps 且分钟级波动。googlevideo 还会 302 到另一个节点并关闭连接，所以几十到几百 KB 的小分片每个都要付一次握手。Shaka 估出 0.2–0.3 Mbps 是真实表现。
- WebView2 强制 CORS，页面不能设 YouTube 要求的 Origin 和 Referer，无法直接取流。
- 客户端策略变化快：YouTube.js 的 TV、MWEB、WEB 在你的网络上被拒。ANDROID 客户端的 30 个格式里只有 1 个带地址（SABR-only）。

原有实现的缺陷
- 备用路径全依赖本机外部工具（yt-dlp、NewPipe 桥接、mpv），应用自己没有取流能力。App.tsx 里内联了 430 多行 YouTube 状态机。
- yt-dlp 没有取消入口，也没有整棵进程树的清理。NewPipe 会自动找桌面上的脚本并执行（GPL 许可加运行本地脚本）。
- CSP 缺 ipc:，每次 invoke 先失败再退回。youtube_playback_capabilities 没有注册。test/youtube.test.ts 在 HEAD 就失败。

我实现中的错误
- 诊断过于绝对：我一开始说“出口 IP 被封”，实测是按视频判定。
- 5 个代码缺陷，都是在真实 WebView2 的端到端阶段暴露的：
  - format_filter 语义写反（它是剔除谓词）。
  - Shaka 重试时重复套代理。
  - /age/ 正则误匹配 “page”，把“页面需要重新加载”判成年龄限制。
  - ANDROID 返回无地址格式，报 “No valid URL to decipher”。
  - yt-dlp 探测超时被报成“未找到”。
- 一次测试断言写错：我按“CONNECT 请求无 UA”识别 Rust 流量，实际 reqwest 的 CONNECT 带 Chrome UA，造成代理场景 6/8 的假失败。
- 换行符判断有误：我曾用 grep -c 判断换行符并据此转换文件。后来用 git ls-files --eol 核实，仓库是 core.autocrlf=true，提交内容一律是 LF，这一步本来就不需要。

协作与环境
- 同一工作树里另一个 agent 在并行开发，它的 EpubReader.tsx 语法损坏，tsc 和 vite build 整体失败（tsc 只要有语法错误，就不报任何语义错误）。我工作期间它还改过 lib.rs。
- pnpm add 清掉了未声明的 pele 链接，pyodide 缺 python_stdlib.zip，tauri dev 锁着 exe。

代码修正（按层）
- 传输层：
  - 本地回环代理：令牌、Host/Origin 校验、域名和请求头白名单、不转发 Cookie、每跳重定向复核。
  - 重定向记忆 15 分钟、连接复用 90 秒加 keep-alive。
  - Shaka 用 700 kbps 起始估计，不信浏览器的乐观带宽。
- 解析层：
  - 过滤无地址、无密文、DRM 的格式。
  - 失败分类：确定性失败立即停，连续 2 次机器人验证就停。
  - Google 的播放器签名脚本在 QuickJS 沙箱里跑（无文件和网络，128 MB，8 秒），按播放器版本缓存到磁盘；BotGuard 解释器通过单独的隐藏 YouTube WebView 执行。
- 进程层：
  - Windows 作业对象终止整棵进程树，并加了取消入口。
  - 解析结果缓存到地址过期。
  - yt-dlp 60 秒，探测 20 秒且超时单独报告。
  - NewPipe 改为只有设置 SEAMIND_NEWPIPE_BRIDGE 才启用。
- 界面层：状态机抽成 YouTubePlayerDialog（关窗即取消、续播进度、自动回退一次），加了诊断面板（代理、分层连通性测试、安装 yt-dlp、会话重试）。
- 配置层：CSP 补 ipc: 和本地代理，注册遗漏的命令，更新失效的测试。

过程
- 端到端放进真实 WebView2 和生产 CSP 里跑。CORS、CSP、MSE 的问题在单测里看不到，上面 5 个缺陷都是这一层暴露的。
- 绕开别人写坏的文件而不是去改它：构建用临时 vite 配置提供 HEAD 版本，类型检查用 compiler host 替换同一文件，端到端用独立 target 目录避开 tauri dev 的锁。

4. 没走的路径

- PO token 和 SABR：这一条是早期暂缓的实现路线；当前工作树已经加入 BotGuard/WebPo token 与 SABR 解析、Shaka 适配，但目标视频的真实播放仍待复测。
- 应用内登录会话：通常能直接过验证，代价是 Cookie 的存储和泄露面，以及账号被限制的风险。目前只保留了 yt-dlp 读浏览器 Cookie 这一条可选路径。
- mpv 直接吃页面 URL：没装 mpv，无法验证，所以没做。
- NewPipe 桥接：保留但默认关闭，因为涉及 GPL 许可。

四、遗留风险与建议

遗留风险
1. 机器人验证是主要限制。
2. 客户端表只管几个月，要对照 yt-dlp 更新 defaultNativeClients。
3. QuickJS 解密路径目前没有真实客户端会触发，只在真实播放器脚本和构造地址上验证过。
4. 我没有在最终代码上做一次性全量回归，mpv 路径也没实测。
5. 官方 yt-dlp 的 SHA-256 校验只能发现下载损坏，不能证明发布者身份。

建议
1. 先做低成本验证：换出口节点后再测那 4 个视频，再试诊断面板的“读取会话并重试”（Firefox）。这能判断瓶颈是出口信誉还是客户端。
2. 先验证当前 BotGuard/WebPo 路径和目标视频能否播放；如果多个出口仍对该视频返回 bot check，再评估用户会话方案及其 Cookie 存储风险。
3. 端到端脚本现在只在会话临时目录里，建议放进仓库（如 apps/desktop/e2e/），别人才能复现。
